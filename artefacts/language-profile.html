Engineering Profile · Language Selection

How I choose
what to build it in

Five languages, ranked by my proficiency, sorted by where each one actually earns its place in the work I do: graph-shaped domain modelling, terminal-first tools, and narrative systems that expose structure rather than hide it. The axis that matters isn't native-versus-web. It's the shape of the artefact and how long I'll have to live with it.

reach for daily reach for rarely
The decisions, one language at a time
01

TypeScript default, on merit

Reach for it whenever the problem is structural: typed entities and the relationships between them.

Nearly everything I build is domain modelling. Graphs, branching clades, parallel world-states. TypeScript's structural typing fits that natively; I can describe a thing by its shape without ceremony, and discriminated unions handle the "this node is one of N kinds" problem that runs through all of it. It isn't the fallback I use when nothing better applies. It's the correct tool for the bulk of the work.

In the wild

The Tongue leans on this constantly: a phonological engine and a cladistic model where every language node is one of a fixed set of kinds, each exhaustively handled. Discriminated unions are doing real load-bearing work, not decoration.

The type system is erased at runtime. It's an expressive lint pass, not a guarantee about the running program; the moment I'm parsing untrusted input where the type lies, that erasure starts to bite.

02

Go single-binary tools

Reach for it when the deliverable is a terminal tool that should ship as one self-contained binary and stay readable solo over years.

The usual pitch (fast, concurrent, great for servers) is true and almost irrelevant to me. The real fit is threefold: one static binary with no runtime to install, the Charm / Bubble Tea ecosystem being the best TUI tooling going, and Go's deliberate austerity meaning the code I write in a hyperfocus burst reads the same cold six months later. The language refuses to let me be clever, which for a solo-maintained tool is a feature.

In the wild

Wyrd (terminal-first directed property graph, Go/Bubble Tea TUI, JSONC flat-file storage) and Iris are correctly Go for exactly this reason. A productivity tool I want to live in should ship as one file with no node_modules and no venv.

The type system is anaemic next to TS. Modelling "one of seven node kinds, exhaustively checked" is ergonomic in TypeScript and a faff in Go; interface-plus-type-switch loses me compile-time exhaustiveness. There's genuine friction between Go's distribution story and its type system for the graph modelling Wyrd needs.

03

Python borrow & leave

Reach for it only to borrow someone else's linguistics or data library, then back out.

Its niche in my work is narrower than its reputation suggests. Where it earns a place is anything touching linguistics, NLP, or corpus tooling where the ecosystem has already solved the problem: IPA manipulation, phonological feature datasets, the work that already exists and would be daft to reimplement.

In the wild

If The Tongue ever ingests real historical language data, or I want to validate the phonological engine against an established model, Python is where that tooling lives. I reach into it for the job and back out.

Its dynamism is the opposite of what I want. I favour systems that expose structure and fail at compile time; Python defers everything to runtime and is happiest when you stop asking it to be rigorous. Not somewhere a project's core should live.

04

C# known, parked

Leave parked unless a native-GUI or heavy-concurrency-service need appears that nothing else covers.

A genuinely well-designed language with a richer type system than Go, but its centre of gravity (enterprise backends, Unity, the Microsoft ecosystem) sits outside my current orbit. I chose Godot for the 2D narrative-archaeology work explicitly for solo-dev ergonomics, which routes around the single most likely reason I'd otherwise touch C#.

When it would resurface

A desktop app needing proper native widgets rather than a TUI, or a long-running concurrent service wanting a richer type system than Go offers. Nothing I'm currently building points there.

Not a weakness in the language so much as in its fit for me right now: it's the one option on this list with the thinnest claim on anything I'm actually making.

05

Rust resist the seduction

Reach for it only when a specific component is both performance- and correctness-critical, and isn't graph-shaped.

The language I'm most likely to want for the wrong reasons. Strong typing, sum types that model "one of N kinds" better than TS does, exhaustive matching, a culture of exactly the structural rigour I'm drawn to. On paper it's my aesthetic ideal, and that's precisely why I should be suspicious of myself reaching for it.

The honest split

For a phonological engine where I want correctness guarantees, Rust's enums and pattern matching outclass everything else here. But a directed property graph with shared, cyclic, mutable back-references is the canonical thing Rust makes painful; I'd end up reaching for Rc<RefCell<>> or arena indices, manually rebuilding what a GC'd language gives free.

Highest ceiling, highest cost. The borrow checker is a continuous tax, heaviest exactly where my work lives. For a solo maintainer it's often the wrong trade, and the appeal is partly aesthetic rather than practical.

The rule, stripped down

  1. TypeScript by default for anything structural, web-facing, or iterating fast on typed relationships.
  2. Go when the deliverable is a CLI or TUI that should ship as one binary and outlive my memory of writing it.
  3. Python only to borrow a linguistics or data library, then leave.
  4. C# parked until a native-GUI or heavy-concurrency need nothing else covers turns up.
  5. Rust only for a component that's performance- and correctness-critical and not graph-shaped. Never the graph core of Wyrd, however pretty the enums look.
